下面给出一套可以直接用于项目改造的完整方案。它不是简单增加提示词，而是把当前的线性 Agent 循环改造成：

> **模型负责语义推理，项目图负责定位与统一表示，Controller 负责阶段、预算、证据、权限和提交条件。**

## 一、先统一七个缺陷编号

后续用 D1～D7 表示：


| 编号 | 缺陷                                                     |
| ---- | -------------------------------------------------------- |
| D1   | 模型可以无限搜索，没有强制进入真实代码或资产阅读         |
| D2   | 模型需要手动复制`node_id`，项目图没有真正成为中间语言    |
| D3   | 通过工具输出是否不同判断进展，而不是判断任务是否真正推进 |
| D4   | 缺少显式任务规划、根因诊断和诊断门控                     |
| D5   | ACI 修改能力覆盖率未知，PowerShell 又可以绕过控制        |
| D6   | 提交条件不完整，没有把诊断、修改和验证组成完整事务       |
| D7   | 上下文参数未经实验验证，过度裁剪可能损害 Agent 能力      |

## 二、改造后的总体架构

建议把 Agent 改造成八阶段状态机：

```
PLAN
  ↓
EXPLORE
  ↓
INSPECT
  ↓
DIAGNOSE
  ↓
EDIT
  ↓
VALIDATE
  ↓
REVIEW
  ↓
SUBMIT
```

允许有限回退：

```
VALIDATE 失败
  ├─ 补丁实现错误 → EDIT
  ├─ 根因判断错误 → DIAGNOSE
  └─ 明确缺少证据 → INSPECT
```

只有满足严格条件，才能从 `INSPECT` 回到 `EXPLORE`。不能因为模型“还想搜一下”就重新开放全局搜索。

# 四、修改方案一：有限探索和候选前沿锁定

## 解决缺陷

主要解决：

```
D1 无限搜索
D3 假进展
D7 反复搜索导致上下文膨胀
```

## 当前问题

现在 `before_action()` 基本只检查某个具体动作签名是否已经被禁用。只要模型换一个搜索词，就会生成新的动作签名并继续执行。候选虽然会被记录，但并不会形成阶段级的强制约束。

## 新增搜索预算

```
@dataclassclassSearchBudget:global_search_limit:int=2global_search_used:int=0graph_expansion_limit:int=3graph_expansion_used:int=0search_extension_limit:int=1search_extension_used:int=0
```

要区分三类操作：

### 全局探索

包括：

```
code_symbol_search
unity_asset_search
unity_object_search
```

默认最多两次。

### 图关系扩展

包括：

```
code_find_references
unity_ref_search
```

它不是重新在整个仓库中盲搜，因此单独计算预算。

### 候选阅读

包括：

```
candidate_read
candidate_expand
```

不属于全局搜索。

---

## 候选前沿

新增统一结构：

```
@dataclassclassCandidateRef:candidate_id:str# C1、C2、C3node_id:str# Controller 内部使用entity_type:strpath:strsymbol:str|Nonerole:str# input/source/controller/ui/test/assetscore:floatreasons:list[str]read_level:str="unread"evidence_ids:list[str]=field(default_factory=list)
```

模型看到的内容是：

```
C1 KitchenGameManager.OnInteractAction
角色：state_controller
路径：Assets/Scripts/KitchenGameManager.cs
原因：包含 WaitingToStart 状态，并引用输入事件

C2 GameInput.OnInteractAction
角色：event_source
路径：Assets/Scripts/GameInput.cs
原因：定义玩家交互事件
```

模型不需要看到或复制内部 `node_id`。

---

## 阶段转换规则

### EXPLORE → INSPECT

满足任意条件即锁定候选：

```
全局搜索已执行 2 次
已有至少 3 个高质量候选
已有状态控制、事件源等互补角色候选
候选置信度超过配置阈值
```

锁定后：

```
关闭全局搜索工具
保留候选阅读和图关系展开
```

模型下一步只能：

```
读取 C1
读取 C2
展开 C1 的调用者
查看 C2 的事件订阅者
```

不能再执行：

```
换一个关键词重新全局搜索
```

---

## 搜索扩展条件

只能通过专用请求：

```
{
  "missing_evidence":"尚未找到订阅输入事件的状态控制器",
  "evidence_ids": ["E3","E5"],
  "requested_entity_role":"state_controller"
}
```

Controller检查：

```
当前候选是否已经充分阅读
缺失项是否具体
是否引用已有证据
是否还有扩展预算
```

通过后只额外开放一次定向搜索。

不能因为模型说“我不确定”就开放。

---

## 验收标准

1. 默认最多两次全局搜索；
2. 第三次无理由全局搜索被拒绝；
3. 搜索预算耗尽后只暴露候选阅读工具；
4. 在固定测试任务中，六次工具调用内必须读取至少一个 Top-3 实现候选；
5. 不同关键词产生不同结果，也不能绕过搜索预算。

# 五、修改方案二：项目图成为真正的中间语言

## 解决缺陷

主要解决：

```
D2 node_id 匹配脆弱
D1 模型看到候选却无法稳定使用
D7 减少长路径和图信息反复进入上下文
```

## 新增 Graph Resolver

文件：

```
src/game_agent/aci/resolver.py
```

定义统一内部引用：

```
@dataclass(frozen=True)classGraphEntityRef:node_id:strentity_type:strpath:str|Nonesymbol:str|Noneasset_guid:str|Nonelocal_file_id:str|Nonehierarchy_path:str|Nonerepository_revision:str
```

Resolver接受模型可能提供的：

```
candidate_id
文件路径
类名
方法名
资产路径
GameObject层级路径
```

统一转换为 `GraphEntityRef`。

---

## 模型接口

模型只调用：

```
{
  "candidate_id":"C1",
  "view":"symbol"
}
```

或者：

```
{
  "path":"Assets/Scripts/KitchenGameManager.cs",
  "symbol":"OnInteractAction"
}
```

Controller内部完成：

```
C1
→ node_id
→ 文件路径
→ 方法范围
→ 文件SHA
→ 调用真实读取工具
```

项目图在这里相当于编译器的中间表示：

```
模型的语义意图
→ 项目图实体
→ 真实代码/资产位置
```

---

## 修改当前实现来源判断

目前不应该再通过：

```
模型调用参数里有没有 node_id
```

判断是否读取了实现代码。

应该使用工具执行后的结构化返回结果：

```
resolved_node_id= (structured.get("node", {}).get("id")orstructured.get("node_id")orresolver.resolve_path(path).node_id
)
```

然后判断：

```
返回节点确实存在
节点属于非测试实现代码
读取范围覆盖了相关实体
证据已记录
```

模型是否手动填写 `node_id` 不再重要。

---

## 歧义处理

例如存在多个 `GameManager`：

```
KitchenGameManager
LobbyGameManager
NetworkGameManager
```

Resolver不能直接猜测，而是返回：

```
R1 KitchenGameManager
R2 LobbyGameManager
R3 NetworkGameManager
```

要求模型选择 `R1/R2/R3`。

但这属于实体消歧，不应重新开放全局搜索。

---

## 验收标准

1. 模型整个任务中可以完全不输出 `node_id`；
2. 只传路径也能生成图支持的证据；
3. 只传 `candidate_id` 可以读取对应代码或资产；
4. 项目图中同名实体会进入消歧，而不是错误匹配；
5. 仓库版本或文件 SHA 变化后，旧引用自动失效。

事件

```

# 七、修改方案四：语义进展账本

## 解决缺陷

主要解决：

```
D3 错误进展判断
D1 不同关键词规避no-progress
D6 提交时缺少可核验阶段记录
```

## 当前问题

当前 `no_progress` 使用工具输出哈希判断。只要连续结果不同，就把 `no_progress_rounds` 清零。不同搜索词返回不同内容，因此即使没有读取根因、没有诊断、没有修改，也会被认为有进展。

## 新增 ProgressLedger

```
classProgressEventType(StrEnum):FRONTIER_IMPROVED="frontier_improved"IMPLEMENTATION_READ="implementation_read"DIAGNOSIS_ACCEPTED="diagnosis_accepted"MUTATION_APPLIED="mutation_applied"COMPILE_PASSED="compile_passed"EDITMODE_PASSED="editmode_passed"PLAYMODE_PASSED="playmode_passed"
```

每个事件：

```
@dataclassclassProgressEvent:event_id:strevent_type:ProgressEventTypephase_before:WorkflowPhasephase_after:WorkflowPhaseevidence_ids:list[str]details:dict
```

只有这些事件使：

```
progress_version+=1
```

---

## 什么不算进展

以下默认不增加版本：

```
换关键词得到不同搜索结果
增加一个低排名且同角色的UI文件
重复读取相同方法
读取同一文件的无关范围
产生不同格式的相同信息
工具输出文本不同但任务状态没变
```

---

## 高质量候选判定

`FRONTIER_IMPROVED` 只在以下情况下产生：

```
候选进入Top-K
候选提高了Top-K最低分
出现新的关键角色
从UI候选找到真正状态控制器
从脚本找到关联Prefab或Scene
候选与失败测试、日志或运行证据发生关联
```

单纯新增文件数量不算进展。

---

## DefaultAgent修改

将当前：

```
ifresult_hash==self._last_result_hash:self.no_progress_rounds+=1
```

替换成：

```
before=self.aci_controller.progress_versionoutputs= [...]after=self.aci_controller.progress_versionifafter==before:self.no_progress_rounds+=1else:self.no_progress_rounds=0
```

输出哈希仍可保留，用于检测完全重复结果，但不再用于判断语义进展。

---

## 分阶段无进展策略

不能所有阶段都直接抛出 `NoProgressExceeded`。

### EXPLORE无进展

```
锁定已有候选
进入INSPECT
```

### INSPECT无进展

```
要求提交当前诊断
或明确指出缺失证据
```

### DIAGNOSE无进展

```
只开放诊断中声明的缺失证据
```

### EDIT无进展

```
要求检查diff或回滚
```

### VALIDATE无进展

```
停止重复验证
返回最后一次确定结果
```

---

## 验收标准

1. 不同关键词搜索不会不断清零无进展计数；
2. 每个进展事件都有对应证据；
3. 任务轨迹中可以明确看到状态如何前进；
4. 验证失败不会被算成成功进展，但会产生新的验证信息事件；
5. 提交时能列出完整进展链。

# 八、修改方案五：显式任务规划和诊断门控

证据需求
根因诊断
因果链
修改计划
验证计划

而不是冗长自由文本推理。

## Controller诊断检查

Controller不直接判断自然语言推理一定正确，但必须检查：

```
root_targets是否来自候选前沿
目标是否已经读取
evidence_ids是否真实存在
证据是否属于当前仓库版本
证据是否覆盖非测试实现代码
修改目标是否包含在根因诊断中
验证计划是否覆盖任务成功标准
是否仍有关键未解决项
```

诊断通过后：

```
DIAGNOSE → EDIT
```

否则返回具体缺口：

```
缺少事件订阅位置证据
C2尚未读取实现代码
E4只证明UI行为，不能证明状态转换根因
```

不能只回复“诊断不完整”。

---

## 修改权限绑定诊断

进入 EDIT 后，只允许修改：

```
proposed_mutations中声明的目标
或诊断批准的相关测试文件
```

模型突然尝试修改其他文件时：

```
阻止修改
要求 diagnosis_revise
```

---

## 验收标准

1. 没有计划不能进入全局探索；
2. 没有接受的诊断不能修改；
3. 诊断必须引用真实证据；
4. 修改目标必须属于诊断目标；
5. 验证计划必须覆盖任务成功条件；
6. 诊断修改会生成新版本，不覆盖旧记录。

# 九、修改方案六：ACI覆盖率验证和受控Shell

## 解决缺陷

主要解决：

```
D5 ACI覆盖率未知和PowerShell绕过
D6 修改无法统一形成事务
```

## 当前问题

动态暴露目前只选择 ACI 工具集合，但底层 `select_agent_tools()` 无论选择了什么，仍然总是加入：

```
PowerShell
Submit
```

同时，`DefaultAgent._execute_action()` 对非 ACI 工具直接调用 `env.execute()`，不会经过 ACI Controller 的证据、checkpoint和验证协议。

---

## 第一部分：真正按状态暴露工具

修改：

```
src/game_agent/framework/models/utils/actions_toolcall.py
```

将：

```

# 十、修改方案七：严格提交契约

## 解决缺陷

主要解决：

```
D6 提交过早
D4 模型可以跳过诊断
D5 Shell修改绕过验证
```

## 当前问题

当前 `guard_submission()` 只在存在未完成 `pending` 修改时阻止提交；如果没有任何修改，`pending is None`，就会直接允许提交。

因此“完全没修改”反而可能更容易提交。

---

## 新增 SubmissionContract

```
@dataclassclassSubmissionContract:plan_accepted:booldiagnosis_accepted:boolmutation_required:boolmutation_count:intno_change_diagnosis_accepted:boolchanged_paths_authorized:booldiagnostics_passed:boolcompile_passed:boolrequired_tests_passed:boolcritical_uncertainties_resolved:boolfinal_review_passed:bool
```

普通修复任务必须满足：

```
plan_accepted
diagnosis_accepted
mutation_count >= 1
changed_paths_authorized
diagnostics_passed
compile_passed
required_tests_passed
critical_uncertainties_resolved
final_review_passed
```

---

## 无需修改的特殊任务

确实无需改动时，不能普通提交，而要提交：

```
no_change_diagnosis
```

要求提供：

```
为什么当前行为正确
读取了哪些代码或资产
使用了哪些证据
执行了哪些验证
为什么任务描述可能与实际不一致
```

Controller批准后才允许零修改提交。

---

## REVIEW阶段

在提交前，Controller自动比较：

```
诊断声明的目标
计划中的修改
实际diff
修改文件范围
验证结果
最终成功标准
```

例如：

```
诊断只批准KitchenGameManager.cs
实际diff还修改了GameInput.cs
```

则 REVIEW 失败，要求：

```
回滚GameInput.cs
或修改诊断并重新验证
```

---

## 验收标准

以下操作必须全部被阻止：

```
没有诊断直接提交
没有修改直接提交
修改后未编译直接提交
只通过EditMode但未通过所需PlayMode直接提交
实际diff超出诊断目标直接提交
存在关键不确定性时提交
```

# 十九、最终验收目标

改造完成后，同一个失败任务应该表现为：

```
1. 模型提交高层计划
2. 最多执行两次全局搜索
3. Controller形成Top-K候选
4. 搜索工具被锁定
5. 模型读取候选代码或资产
6. Controller自动完成图节点匹配
7. 模型提交带证据的根因诊断
8. Controller批准修改目标
9. 模型通过ACI或受控Shell修改
10. 自动执行编译、EditMode和PlayMode
11. Controller比较诊断、diff和验证结果
12. 满足提交契约后开放submit
```

对应你当前失败案例，最低验收标准可以设为：

```
全局搜索次数 ≤ 2
根因实现文件读取调用序号 ≤ 6
必须产生结构化诊断
必须产生至少一个mutation transaction
不能通过普通PowerShell绕过修改门控
提交前必须完成要求的Unity验证
不再因为Token耗尽结束于定位阶段
```

最重要的改造优先级是：

```
第一：搜索预算和候选锁定
第二：Graph Resolver和candidate_id
第三：结构化诊断门控
第四：语义进展账本
第五：统一修改事务和提交契约
第六：上下文参数实验
```
